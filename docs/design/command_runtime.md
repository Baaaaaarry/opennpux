# Command Runtime

## Objective

The command runtime replaces the fixed-address DMA smoke contract with a versioned command
descriptor that can carry real inference operations. The first operator is
`VECTOR_ADD_U32`; it validates the complete CPU-to-NPU submission path before
DS4 tensor formats and operators are added.

The generic `.npxm` container stores a bounded operator list and its input
tensors. The runtime validates all file offsets and tensor sizes before
dispatch, so model loading is independent of any specific inference framework.
The sample model deliberately mixes an official software node and a custom RTL
node to exercise heterogeneous scheduling.

## Shared Window Layout

The existing 4 KiB coherent shared window is partitioned as follows:

| Offset | Size | Purpose |
| --- | ---: | --- |
| `0x000` | 64 B | versioned command descriptor |
| `0x100` | 1024 B | input tensor 0, up to 256 `uint32_t` elements |
| `0x500` | 1024 B | input tensor 1 |
| `0x900` | 1024 B | output tensor |

Every address in the command is an offset relative to the shared window. The
firmware rejects an unsupported ABI, opcode, element count, alignment, or
out-of-window tensor range.

The ABI is mirrored in:

- `runtime/host/include/opennpux/coral_command.h`
- `sim/coralnpu/hw_sim/gem5_bridge/coral_command.h`

`tools/coralnpu/check_command_abi.sh` prevents a build when they differ.

## Submission Flow

1. Linux runtime maps `/dev/opennpux-coral` shared memory.
2. CPU fills both inputs and a pending command descriptor.
3. Runtime issues driver `START` and blocks in `poll()`.
4. Coral firmware validates the descriptor and executes vector addition.
5. Firmware writes output, completed element count, and completion status.
6. Driver wakes userspace; runtime validates every output and reports checksum.

After consuming a terminal status, the runtime acknowledges completion through
the reset ioctl. This permits back-to-back commands on one open device without
racing the driver's delayed completion worker.

This path uses the same driver, coherent gem5 DMA, Coral AXI master, and
Verilated official core that later DS4 operators will use.

## Future Workload Adapters

Future workload adapters should retain this descriptor header and add:

- signed and quantized tensor metadata;
- dense/matrix-vector and activation opcodes required by DS4;
- framework-specific graph partitioning;
- operator-specific performance counters where required.

Model-level output already includes host end-to-end simulated time and custom
accelerator cycle totals. DMA request, completion, and error deltas report the
memory traffic generated by the complete model.
